## Design Specificity Verdict

**Authored for this product, with one telling gap.**

**LLM assessment:** Content is unmistakably CC-GUI — commander chip, cascade unpin, harness picker, review-comment staging, split-pane quadrants. Token discipline is textbook: mono keys / sans descriptions, semantic tokens throughout, reuses the palette's exact overlay signature (scrim, `--radius-3`, `--shadow-raised`, `overlay-in 0.13s`). But it diverges from its own sibling overlay: the command palette has a header with a `Cmd+K` glyph and an uppercase ESC-hint chip; the help overlay has neither. And the help for a keyboard-first, fuzzy-palette app is itself not keyboard-operable — no filter, no in-overlay navigation, overflow reachable only by mouse. That is the biggest missed opportunity for character.

**Deterministic scan:** `detect.mjs --json src/help.ts` → exit 0, `[]` (no antipatterns; help.ts builds DOM programmatically with no inline styles). No hardcoded hex/rgba in the help CSS (DESIGN.md ban upheld).

**Visual overlays:** none — no browser/screenshot driver in a native WKWebView app.

## Overall Impression

A genuinely clean, expert-appropriate reference that wears all 19 themes for free and speaks the tool's own vocabulary. What holds it back is accessibility/keyboard reachability and a drift from the palette pattern it clearly derives from. Biggest single opportunity: make the help behave like the palette it resembles — filterable, keyboard-scrollable, with a real dialog contract.

## What's Working

1. **Mono-for-data honored precisely** (`style.css:2040-2048`) — keys in `var(--font-mono)`/`--subtext1`, descriptions in sans/`--text`. Keys pop as scannable anchors.
2. **Zero raw color; full reskin** — scrim, elevated bg, strong border, radius-3, raised shadow, 0.13s entrance all tokenized; inherits every theme.
3. **Content authored for experts** — every row assumes fluency (cascade unpin, quadrant split preview); no onboarding filler, matching the stated product principle.
4. **Restraint in the dynamic section** (`help.ts:125-135`) — the CC-config keybindings block stays hidden until rows arrive, avoiding an empty-header stub. Reduced-motion honored (`style.css:4344-4350`).

## Priority Issues

**[P1] No dialog semantics or focus management** — `help.ts:82-89, 140-142`
Bare `<div id="help-overlay">`: no `role="dialog"`, no `aria-modal`, no accessible name; opening never moves focus into the box, closing never restores it, no focus trap. Screen-reader users get no announcement; Tab escapes behind the scrim.
*Fix:* add `role="dialog" aria-modal="true" aria-label="CC-GUI keyboard reference"`, focus the box on open, restore prior focus on close.

**[P1] Overflow content is keyboard-unreachable** — `style.css:1996-2000`
`.help-box` is `max-height:75vh; overflow-y:auto`, but focus never enters the box and `body` is `overflow:hidden`. On a short window (e.g. 4-pane split active) the lower sections + appended keybindings table cannot be scrolled to by keyboard at all.
*Fix:* give `.help-box` `tabindex="-1"` and focus it on open (also satisfies the P1 above) so PageDown/arrows scroll it.

**[P2] No exit affordance or hint** — `help.ts:85-89`
Unlike the documented palette, no ESC-hint chip and no ✕. Exit relies on tribal knowledge.
*Fix:* add the palette's uppercase ESC-hint chip in a small header row beside the `<h2>`.

**[P2] Masonry produces unpredictable reading order** — `style.css:2014-2017`
`column-count:2` balances by height, so section-to-column assignment and overall scan order shift with content and window height. "Terminal" is never in a fixed place.
*Fix:* use a deterministic two-column grid with explicit section order (or single column).

**[P3] Overloaded "Path input" cell** — `help.ts:20`
Five behaviors (Tab / ↑↓ / Enter drill / Enter commit / Browse…) in one `dd` where every other row is atomic.
*Fix:* split into two rows or shorten.

## Persona Red Flags

**Sam (accessibility / keyboard / screen-reader) — critical, multiple failures:**
- `help.ts:82-86` — no `role`, `aria-modal`, or label; invisible as a dialog to assistive tech.
- `help.ts:140-142` — no focus move-in, no focus trap; Tab reaches the obscured app behind the scrim.
- `style.css:1999-2000` — scrollable overflow unreachable without a pointer (worst offender).
- Focus not restored on close.
- Minor: h3 headings not programmatically associated with their `dl`s, so groups read as one long list.

**Alex (power user) — ironic friction:** the reference for a keyboard-first tool has no filter, no find, no keyboard scroll. Alex expects to fuzzy-filter 45 rows the way `Cmd+K` filters everything else; here they can't.

**Riley (stress tester):** open `?` on a short window with a 4-pane split — keybindings section overflows below 75vh, mouse-only to reach. Also the always-attached document keydown listener (`help.ts:150-158`) closes help on Esc regardless of `inInput`, so pressing Esc to clear something else while help is open closes help instead — a mild surprise.

## Minor Observations

- Title "CC-GUI help" (`help.ts:88`) is generic vs the system voice; "Keyboard reference" would fit better.
- `dt` keys at 11px mono are at the legibility floor; fine for experts, tight otherwise.
- `.help-box h3` uses `--text-dim` at 11px uppercase — smallest + dimmest layer, a legibility risk under some themes.
- No `:focus-visible` styling inside the overlay — nothing to show focus even once focus management exists.
- No media query governs `.help-box` (fixed 520px) — only vertical `overflow-y:auto` handles a small window; width never adapts.
- Overlay + listeners created at import time and never torn down (cheap, just noted).

## Questions to Consider

- In a tool whose identity is `Cmd+K` fuzzy search over everything, why can't you fuzzy-search the help? A palette-style filterable list would resolve masonry order, recall, and keyboard reachability at once — and be maximally on-brand.
- The palette and help are near-identical overlays. Should help just *be* a palette mode (a "?" scope) rather than a separate component that has already drifted from the palette pattern?
- If the audience never needs onboarding, is a 45-row static wall the right artifact, or should shortcuts surface contextually on the surfaces they belong to?
