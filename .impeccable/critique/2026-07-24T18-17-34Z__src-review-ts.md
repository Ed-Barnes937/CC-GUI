## Design Specificity Verdict

**Authored for this product — not category-interchangeable.** This is not a generic GitHub-PR clone. The stranded-file section and "Unanchored comments" orphan section exist *because* the diff can mutate under the reviewer while comments persist (review.ts:455-471, 661-668, 772-776); the apply bar says "ready to send back to the agent" (review.ts:949); the `deferred` outcome references a brief written for a not-yet-ready agent (model.ts:147); `buildDraft` mirrors the TUI's new-side-wins rule (model.ts:110-122). Someone who understood the agent-round-trip domain built this.

**Deterministic scan:** `detect.mjs --json index.html src/review.ts` returned `[]`, exit 0 — clean, zero findings. This corroborates heuristic 8: the theming contract is fully honored (no hardcoded hex/rgba anywhere in the review CSS; every color is `var(--token)` or `color-mix` off a token). No false positives to flag.

**Visual overlays:** unavailable — native WKWebView with no browser automation/screenshot driver in this session. Evidence gathered from DOM-building code and CSS, as instructed.

The one drift toward generic-review-tool is the comment card chrome (a "y / you" avatar + speech-bubble emoji), which imports a GitHub-comment mental model this single-user local tool doesn't need.

## What's Working

1. **Honest handling of a diff that mutates under the reviewer.** Stranded files (review.ts:455-471) and orphan comments (review.ts:661-668, 772-776) are surfaced, kept selectable and deletable rather than dropped — the hard product-specific case, handled with care and explained in comments.
2. **Failure reassures; blocked state is legible.** The `blocked` branch keeps the surface open (review.ts:962-968) and drifted comments stay pinned with delete buttons; the `--attention` tint on tag/border/orphan-header (style.css:3739-3741, 3917-3919, 3965-3968) forms a coherent "this needs you" language.
3. **Genuine power-user efficiency and clean theming.** Per-file token cache reset on refresh (review.ts:150-151, 249), on-demand Shiki lang/theme loading (review.ts:65-97), re-highlight-in-place on theme change (review.ts:283-288), resizable persisted sidebar (review.ts:205); detector-confirmed zero raw colors.

## Priority Issues

**[P0] Success feedback is written to a node that is immediately hidden.**
- Where: review.ts:961-967. `statusEl.textContent = describeOutcome(outcome)` then `closeReview()` hides `#review` in the same tick.
- Why it matters: the single most important moment — did my review reach the agent? — produces no visible acknowledgement from this surface. Failure reassures (stays open); success evaporates. The peak-end is mishandled.
- Fix: raise a persistent toast/confirmation outside `#review` before closing, or hold the panel with an inline "sent" state (you already render the `applied` comment state) so the reviewer sees what landed.
- Suggested command: `$impeccable harden`

**[P1] No keyboard path to create a comment, in a surface briefed for full keyboard operability.**
- Where: selection is click/shift-click only (review.ts:746-755); the keyboard listener moves *files*, not a line cursor (review.ts:991-1001). Diff lines are clickable `<div>`s with no role/tabindex/key handler (confirmed by B).
- Why it matters: the core action of the surface is unreachable without a mouse, directly contradicting the product's "full keyboard operability" commitment.
- Fix: add a focused-line cursor (j/k or ↑/↓ when not in file-nav mode), Enter/`c` to open the composer, shift+arrows to extend the range — mirror the TUI's line selection.
- Suggested command: `$impeccable harden`

**[P1] The overlay is not a real dialog: no focus move, no trap, no role/aria-modal.**
- Where: index.html:82 (`<div id="review" class="hidden">`, no role) and review.ts:220-230 (`openReview` never moves focus in). `#review` is `position:fixed; inset:0; z-index:10` (style.css:3493-3500) painting over the app, yet Tab can walk into the obscured workspace behind it.
- Why it matters: keyboard/AT users land nowhere on open and can tab out of the visible surface into hidden controls.
- Fix: `role="dialog" aria-modal="true"`, move focus to the panel (or first file row) on open, restore on close, trap Tab within.
- Suggested command: `$impeccable harden`

**[P2] No focus-visible styling on buttons; focus ring exists only on the juxtapose slider.**
- Where: `.apply-btn` (style.css:3814-3830), `.editor-save`/`.editor-cancel` (3861-3881), `.comment-delete` (3887-3898), header `×`/`↻`, plus the textarea has `outline:none` with no focus-state (3832-3843). Only `.review-image.juxtapose:focus-visible` draws a ring (4042-4044).
- Why it matters: a keyboard user tabbing to Apply — the irreversible action — cannot see where focus is.
- Fix: add a `:focus-visible` ring token to every interactive control in the surface; reuse the `--accent` ring pattern already on the slider.
- Suggested command: `$impeccable harden`

**[P2] The one irreversible action has no confirmation and no undo.**
- Where: review.ts:954-974. "Apply N comments →" immediately posts to the agent and, on success, closes everything. The target sits at the bottom edge where mis-clicks happen.
- Why it matters: "sent to the agent" is not reversible; Operate mode tolerates less hand-holding but not a silent, unrecoverable send.
- Fix: require a modifier / second-press confirm on Apply, or a brief post-apply undo window; at minimum keep the surface open with an explicit "sent" state (folds into P0).
- Suggested command: `$impeccable harden`

**[P3] Raw error interpolation as user-facing copy, in low-salience chrome.**
- Where: review.ts:242, 320, 569, 595, 970 — Rust error `Display` strings land verbatim in 12px `--warning` text in the header corner (style.css:3790-3793).
- Why it matters: failures are both ugly and easy to miss.
- Fix: map known failures to sentence-case copy; keep the raw error behind a hover/title or log; raise failures with the salience of the blocked state.
- Suggested command: `$impeccable clarify`

## Persona Red Flags

**Alex (power user):** The reviewed-toggle (15×15px, style.css:3643-3654) and comment-delete `✕` (11px, padding 0 2px, style.css:3887-3894) are mouse-only pinpricks easy to fat-finger against row-select. There is no keyboard toggle for "reviewed," so the progress ring can only advance by mouse — an odd gap for the persona this surface is built for.

**Sam (accessibility/keyboard/contrast):** (1) Cannot create a comment without a mouse (review.ts:746-755). (2) No focus ring on Apply/Save/Cancel/delete/close/textarea (style.css:3814+, 3832-3843, 3861+, 3887+). (3) No focus management or dialog semantics on open (index.html:82; review.ts:220-230). Contrast: `.comment-tag.comment-applied` is `--text-dim` text on a `--text-dim` 18% fill (same hue, style.css:3970-3973) — highest risk; plus small `--text-dim` text throughout (progress-label 10.5px uppercase, comment-range). The slider sets `aria-valuenow` but no `aria-valuetext` (review.ts:902), so a screen reader announces a bare number.

**Riley (stress tester):** (1) The comment-count emoji (review.ts:433, 504) renders inconsistently across WKWebView font stacks and is the sole carrier of "N comments" with no title/aria-label (confirmed by B). (2) Rename edge case: comments key to `c.file` vs `displayPath` = `new_path` for renames (model.ts:80-82; review.ts:255-256, 458-461) — a comment authored against the old path before a rename could be mis-stranded into "no longer in the diff"; worth a targeted test. (3) Progress-ring "done" count is correctly clamped to files still in the diff (review.ts:356-358) — the obvious overflow attack is already defended.

## Minor Observations

- **Accent is not scarce** as the design system claims: `--accent` paints every hunk header (style.css:3733), the comment count (3718), selection (3783), and the slider divider/handle (4060, 4072). A color on every hunk down a long file has no signal value left — reserve it for selection; give hunk headers a quieter `--text-dim`/`--bg-elevated` treatment.
- **Redundant count**: summary "N comments ready…" (review.ts:949) and button "Apply N comments →" (review.ts:951) state the same number 12px apart.
- **The "y / you" avatar** (review.ts:527-530) is GitHub muscle memory in a single-user local tool — every comment is "you." Dropping it reclaims space and removes an `--info` fill that competes with the status tag.
- **Two range formats** for the same concept in the same card family: en-dash range (review.ts:545) vs "lines A–B" (review.ts:610).
- **Fixed 100px comment indent** (`.review-comment { margin: … 100px }`, style.css:3905) eats horizontal room on a narrow diff pane regardless of pane width.

## Questions to Consider

- The surface is a fixed full-screen overlay (style.css:3493-3500). For a maintainer whose north star is "what needs you / what's in progress," why does reviewing a diff hide the workspace entirely rather than dock beside it? The overlay model is what forces the abrupt close-on-apply that breaks the ending.
- On success Apply closes the review; on block it stays. Should success instead leave the reviewer in the diff with applied comments greyed (you already render `applied` state) so they see what landed and can keep going — turning the peak-end from "everything vanished" into "here's what you sent"?
- If a comment can drift and block apply, is there value in showing drift proactively on refresh (a count in the apply bar) rather than only at the moment Apply is rejected?
