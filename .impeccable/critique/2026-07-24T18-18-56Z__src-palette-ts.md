## Design Specificity Verdict

**Authored for this product — not a category-interchangeable cmdk clone.**

**LLM assessment:** The palette is shaped for expert, keyboard-first, themeable CC-GUI. Session rows carry a project-identity square + project name + a live state pill reusing the shared `status-chip` vocabulary (`palette.ts:142-156`), so a session reads identically in the palette and the sidebar. Commands carry tinted rounded-square glyph icons keyed to semantic tones (`main.ts:4044-4120`) and right-aligned keybinding glyphs pulled live from the user's config via `kb()` (`main.ts:4339`) — the palette doubles as a shortcut cheat-sheet that can't drift from config. Everything is tokenized (`--scrim`, `--bg-elevated`, `--radius-3`, `--shadow-raised`, `overlay-in 0.13s`). Where it falls short is depth of the keyboard/a11y model, not authored intent.

**Deterministic scan:** `node .claude/skills/impeccable/scripts/detect.mjs --json src/palette.ts` returned `[]`, exit 0 (clean). This is a genuine clean result, not a miss: `palette.ts` builds DOM via `createElement` + `className` + `textContent` with no inline `element.style` and no raw color literals, so the markup-oriented detector has nothing to flag. Its scope does not cover CSS-side issues (fonts, radii, ARIA), which is where the manual code evidence surfaced everything below.

**Visual overlays:** Unavailable. Native WKWebView Tauri app with no browser automation / screenshot driver in this session — no live overlay, computed-style, or contrast inspection was possible. All evidence is from code + CSS.

## Overall Impression

A well-authored, product-specific palette with a correct safety model, let down by an under-built keyboard/feedback layer. The two things a keyboard-first tool must nail — *where am I in the list* and *did anything happen* — are the weakest points: the selection cursor is faint and can scroll off-screen, and a no-match query produces a silent blank box. The single biggest opportunity is hardening the keyboard + feedback loop; the visual language is already right.

## What's Working

1. **Live, config-driven shortcut glyphs + semantic-tone command icons.** `kb()` resolves the user's actual keybinding (`main.ts:4339`); tinted squares (`success`/`danger`/`info`/`dim`) give scannable command categorization. Expert density done right.
2. **Sessions rendered in the sidebar's own status language.** Project square + name + state pill via shared `status-chip` classes (`palette.ts:142-156`) — zero re-learning between surfaces.
3. **Restrained, correct safety model.** The one destructive palette entry (Delete merged-PR) is guarded with a count/preview/consequence dialog (`main.ts:2681-2684`), and irreversible per-session actions (kill/restart/delete) are kept out of the fast Enter path entirely. Error prevention by information architecture, not just confirm dialogs.

## Priority Issues

### [P1] Keyboard selection can scroll off-screen (no scroll-into-view)
- **Why it matters:** Arrow nav updates `selected` and re-renders but never scrolls the row into view (`palette.ts:192-199`). The list caps at 30 rows in a `max-height:60vh` box; past ~15 rows the cursor moves below the fold invisibly. In a keyboard-first tool the cursor is the only affordance for where you are.
- **Fix:** After appending rows, scroll the selected one: `if (i === selected) row.scrollIntoView({ block: "nearest" });` near `palette.ts:181`.
- **Suggested command:** `$impeccable animate` (motion/scroll behavior) or `$impeccable harden`

### [P1] Selection indicator is too weak and collides with hover
- **Why it matters:** `.palette-row.selected` and `.palette-row:hover` share one rule filling with `var(--border)` (`style.css:1904-1906`) — low contrast against `--bg-elevated`, and keyboard selection is visually identical to mouse hover, so moving the mouse creates two "selected-looking" rows in a fire-on-Enter surface.
- **Fix:** Give `.selected` a distinct higher-contrast treatment (`background: var(--bg-inset)` or a 2px `--accent` left border) separate from `:hover` at `style.css:1904`.
- **Suggested command:** `$impeccable layout` or `$impeccable colorize`

### [P1] Focus management breaks the keyboard-first commitment
- **Why it matters:** Full keyboard operability is a stated brand commitment. Today: no focus trap, so Tab escapes the modal into the scrimmed background controls; Escape is handled only in the input's keydown (`palette.ts:191`) while the document handler covers only Cmd+K (`palette.ts:209-214`), so once focus leaves the input, Esc no longer closes the palette; and `closePalette` never restores focus to the pre-open element (`palette.ts:87-89`), landing the user on `<body>` and breaking subsequent element-scoped shortcuts.
- **Fix:** Trap Tab within the palette, handle Escape at the overlay/document level, and capture the opener in `openPalette` to `.focus()` it in `closePalette` (`palette.ts:78-89`).
- **Suggested command:** `$impeccable harden`

### [P2] Screen-reader semantics are absent
- **Why it matters:** The palette implements a combobox+listbox visually but exposes almost nothing to assistive tech. Missing: `role="dialog"`/`aria-modal` on the overlay (`palette.ts:52`), `aria-label` on the input (placeholder only, `palette.ts:63`), `role="listbox"` on the list, `role="option"`/`aria-selected` on rows (selection is a pure visual class toggle, `palette.ts:137`), and `aria-activedescendant` on the input. A screen-reader user gets no announcement of the highlighted row.
- **Fix:** Add the dialog/listbox/option roles, `aria-selected` on the active row, row `id`s + `aria-activedescendant` on the input, and an input `aria-label` (`palette.ts:52-135`).
- **Suggested command:** `$impeccable harden`

### [P2] No-results state is a blank void
- **Why it matters:** When a query matches nothing, `filtered` is empty and `renderList` produces an empty container (`palette.ts:123-124`). The user sees a blank box under their query with no acknowledgement — can't tell if the palette is broken or just empty. Weakest emotional moment and easiest fix.
- **Fix:** In `renderList`, when `filtered.length === 0` append a `.palette-empty` row with "No matching sessions or commands" (`palette.ts:124`).
- **Suggested command:** `$impeccable clarify` or `$impeccable onboard`

## Persona Red Flags

**Alex (power user):** ArrowUp/Down are not `preventDefault`'d (`palette.ts:192-199`), so they move both the list cursor and the text caret in the input, fighting each other mid-query. No wrap-around at list ends (`palette.ts:193,197`). No match highlighting — `score()` computes match positions (`palette.ts:34-50`) but `renderList` discards them and sets plain `textContent` (`palette.ts:141`), so Alex can't see why a fuzzy result ranked. Selection lost below the fold is the single most disruptive one for a fast typist.

**Sam (accessibility):** Every item in the screen-reader gap hits Sam — no listbox/option roles, no `aria-activedescendant`, no focus trap, no focus restore, unlabeled input; effectively unusable via screen reader and leaks focus to the background on Tab. The faint selected-row contrast also fails low-vision users who rely on the visible cursor.

**Riley (stress-tester):** Long titles ellipsize cleanly (`style.css:1909-1914`) — good. But with 30+ concurrent sessions the global `entries.slice(0,30)` (`palette.ts:105`) fills the list with sessions and the Commands group never appears on empty-open. Rapid Esc after focus has drifted off the input does nothing (Esc only bound on input). Hammering ArrowDown past row 30 silently clamps with the cursor already off-screen.

## Minor Observations

- **Shortcut glyphs are not Mono.** `.palette-shortcut` (`style.css:1986`), `.palette-kbd` (`style.css:1854`), `.palette-esc` (`style.css:1870`) set no `font-family` and inherit `--font-ui` (Plex Sans), violating the Mono-for-Data rule that `.help-table dt`, `.onboarding-kbd`, and `.pr-badge` all follow. Internally consistent with `.menu-shortcut`, at least.
- **Off-scale radii:** `.palette-esc` `border-radius: 4px` (`style.css:1877`) and `.palette-icon` `border-radius: 6px` (`style.css:1929`) are off the 7/10/12+pill token scale; the comparable `.onboarding-kbd` uses `--radius-1`.
- **`hint: "command"` filler.** Entries without a shortcut render their `hint` string, and many hints are the literal word "command" (`main.ts:4076-4095`), putting meaningless right-aligned labels in rows. It also pollutes fuzzy matching — `score()` matches against `` `${e.label} ${e.hint}` `` (`palette.ts:107`), so "com" surfaces every command by its hint.
- Group labels always render even for a single group (`palette.ts:128-133`).
- Good details: `noTextAssist` kills autocomplete/spellcheck on the input (`palette.ts:62`); reduced-motion is honored for the overlay-in animation (`style.css:4344-4350`); all colors are tokenized (no raw hex/rgba in palette code or CSS); no inline `element.style` bypassing the token system.

## Questions to Consider

1. If the target user runs dozens of sessions, should empty-open lead with **commands** (finite, memorizable) and defer sessions until typed — the inverse of today's session-first ordering?
2. The palette shows a session's live **state pill** but offers only **Attach**. Should a "needs-you" session be one keystroke from its resume/review action, or does navigation-only preserve the safety model deliberately?
3. Fuzzy match positions are computed and thrown away. Is un-highlighted fuzzy matching worse than plain substring for an expert who can't verify why a match ranked?
