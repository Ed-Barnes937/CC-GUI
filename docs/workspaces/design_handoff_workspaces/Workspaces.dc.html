Turn 1 · claude-commander workspaces
Workspaces in the Console and Board
Upstream, a workspace is a label on a project; untagged projects belong to the built-in Main. Switching is a hard client-side filter: the sidebar, tab strip, board columns, title-bar counts and attention pill all scope to the active workspace. Sessions in other workspaces keep running. Mocks use a Work workspace (atlas-api, web-app, infra) with Main (cc-gui, claude-commander) and OSS (dotfiles, ratatui-widgets) alongside.
1a Title-bar switcher
A workspace chip beside the claude-commander name. It lives in the title bar, so Console and Board share one switcher and the scope stays visible in both. Keyboard: ⌘⇧1–9 jumps directly, and ⌘K gets "Switch workspace" commands.
Board, same workspace: columns only hold Work sessions, and the project filter lists only Work projects.
Chip open: workspaces in display order with project counts and shortcuts, plus create and manage.
Management flows
All built on the 1a title-bar chip.
1c Move project to workspace
A new submenu on the project header's context menu. "New workspace…" creates the workspace and moves the project into it in one step, since the server defines a workspace on first use.
Or drag a project header onto the workspace chip: it opens the menu, and dropping on a workspace moves the project there.
1d Settings › Workspaces
"Manage workspaces…" opens this panel. Here you create, rename, reorder and delete workspaces, and set each one's theme, the startup workspace (last / main / named) and Main's label. Names follow the upstream rules: 40 characters max, and "main" and "last" are reserved.
1e Delete workspace
Uses the existing confirm dialog. It spells out the consequence: the projects move to Main, and nothing is stopped.
1f Per-workspace theme
OSS is set to Tokyo Night (see 1d), so switching to it re-skins the chrome, terminal and diffs. That makes a workspace change obvious at a glance. Like the TUI's [workspace_themes], the theme is stored locally and keyed by workspace name.
